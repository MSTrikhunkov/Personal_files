# Обоснование исправлений python-ldap 3.4.4

Дата анализа: 2026-09-18. Объект — предоставленный `python-ldap-3.4.4.tar.gz`, каталог внутри архива `python-ldap-python-ldap-3.4.4`. Обе CVE подтверждаются исходниками и воспроизводятся регрессионными тестами. Оснований признать их неприменимыми к этой версии нет; фактическая экспозиция приложения зависит от передачи недоверенных значений соответствующим функциям.

## CVE-2025-61912 — применима, исправлена

В `Lib/ldap/dn.py`, функции `escape_dn_chars`, NUL заменялся на backslash и буквальный NUL. Результат не являлся корректным RFC 4514 представлением и мог приводить к клиентской ошибке при дальнейшей передаче DN в LDAP API.

Без изменений перенесён production-hunk [коммита 6ea80326a34ee6093219628d7690bced50c49a3f](https://github.com/python-ldap/python-ldap/commit/6ea80326a34ee6093219628d7690bced50c49a3f): NUL кодируется текстовым `\00`.

Обновлено upstream-ожидание теста специальных символов. Добавлены случаи NUL в начале, середине и конце, повторные NUL, проверка отсутствия буквального NUL в результате и round-trip через `ldap.dn.str2dn` с реальным нативным `_ldap`. Отдельно проверено, что буквальный backslash с двумя нулями не смешивается с NUL. До исправления DN-набор имел 5 assertion failures с учётом subtests; после все 8 тестовых методов проходят.

Исправление не гарантирует принятия такого DN любым сервером: серверная политика может запрещать NUL в конкретном атрибуте. Оно исправляет экранирование на клиенте.

[Официальное уведомление GHSA-p34h-wq7j-h5v6](https://github.com/python-ldap/python-ldap/security/advisories/GHSA-p34h-wq7j-h5v6) указывает исправление в 3.4.5.

## CVE-2025-61911 — применима, исправлена

В `Lib/ldap/filter.py`, функции `escape_filter_chars`, при `escape_mode=1` отсутствовала проверка строкового типа. Итерация по специально подобранному list/dict обрабатывала целые строки как отдельные элементы и позволяла оставить управляющие символы фильтра неэкранированными.

Без изменений перенесён production-hunk [коммита 3957526fb1852e84b90f423d9fef34c7af25b85a](https://github.com/python-ldap/python-ldap/commit/3957526fb1852e84b90f423d9fef34c7af25b85a): `isinstance(assertion_value, str)` и `TypeError` до выбора режима. Преобразование произвольных объектов в строки не добавлялось.

Перенесены upstream-тесты со списком и словарём, содержащими `abc@*()/xyz`. Дополнительно проверяются нестроковые типы во всех режимах, пустые контейнеры, bytes/bytearray, обычные строки, подкласс str, пустая строка, NUL и символы LDAP-фильтра. До исправления проверки отклонения входов давали failures/errors; после все 5 тестовых методов проходят. Алгоритмы экранирования строк и поведение трёх режимов не менялись.

[Официальное уведомление GHSA-r7r6-cc7p-4v5m](https://github.com/python-ldap/python-ldap/security/advisories/GHSA-r7r6-cc7p-4v5m) и [релиз 3.4.5](https://github.com/python-ldap/python-ldap/releases/tag/python-ldap-3.4.5) описывают это исправление.

## Совместимость и границы переноса

Из производственных файлов изменены только `Lib/ldap/dn.py` и `Lib/ldap/filter.py`. Версия 3.4.4, публичные сигнатуры, metadata, Python >=3.6 и зависимости остались прежними. Изменения C-расширения, схем, серверной конфигурации и иных функций не требуются и в патчи не входят.

Формально меняется ошибочная обработка NUL и недопустимых нестроковых аргументов. Это целевые изменения безопасности из апстрима. Подклассы str разрешены, корректные строковые входы сохраняют поведение. Код и тесты используют синтаксис, доступный в Python 3.6; выполнение на самом Python 3.6 не проверялось.

## Проверки и ограничения окружения

Собрано настоящее C-расширение `_ldap` отдельно для CPython 3.9.6 и 3.12.14. Платформа — macOS; LDAP API сообщает OpenLDAP vendor_version 20428 (2.4.28). Использованы pyasn1 0.6.4 и pyasn1_modules 0.4.2. Моки нативного LDAP-парсера не применялись.

| Проверка | До | После |
|---|---|---|
| macOS-набор из исходного tox.ini, Python 3.9 | 68 tests, OK, expected failures=1 | 72 tests, OK, expected failures=1 |
| тот же набор, Python 3.12 | — | 72 tests, OK, expected failures=1 |
| DN + filter, Python 3.9 | уязвимости воспроизведены | 13 tests, OK |
| DN + filter из собранного wheel | — | 13 tests, OK |
| полный discovery, Python 3.9 | 104 tests, 12 errors, expected failures=1 | 108 tests, те же 12 errors, expected failures=1 |

Единственный expected failure обозначен самим апстримом: `Tests.t_ldapurl.TestLDAPUrl.test_bad_urls`. В macOS-наборе использована предусмотренная tox переменная `CI_DISABLED=INIT_FD`.

Полный discovery выполнен с `SLAPD=/usr/libexec/slapd`, временными данными в `WORK/ldap/tmp` и тем же `CI_DISABLED=INIT_FD`. Список ошибок до и после совпадает:

- 11 ошибок запуска/подготовки локального slapd: системный `slapadd` не принимает требуемую конфигурацию, выдавая `invalid value for attributeType objectClass` и `could not parse entry (line=14)`. Затронуты `t_bind`, `t_cext`, `t_edit`, `TestLDAPObjectOptions`, `t_ldap_sasl`, `TestSubschemaUrlfetchSlapd`, `t_ldap_syncrepl`, оба класса `t_ldapobject` и два теста `t_slapdobject`.
- `t_ldap_options.TestGlobalOptions.test_cafile`: чтение `OPT_X_TLS_CACERTFILE` в системном LDAP вызывает `ValueError: option error`.

Ошибки не исправлялись посторонними изменениями библиотеки и не маскировались изменением тестов. Полный серверный набор в данном окружении не прошёл; часть классов не смогла начать тесты. Для проверки на целевой Linux-платформе требуется совместимый OpenLDAP/slapd и его схемы/TLS. Проверенные DN round-trip и filter regression tests от этих серверных ограничений не зависят.

Дополнительно успешно выполнены:

- Сборка `setup.py sdist bdist_wheel`.
- Установка wheel через `pip --no-deps --target` в рабочий каталог; проверены версия 3.4.4 и импорт Python-модулей/нативного `_ldap` именно из этого каталога.
- Независимое read-only ревью: production-изменения совпадают с апстримом, замечаний нет; рецензент отдельно выполнил 13 тестов DN/filter на Python 3.9.
- `git diff --check`.
- `git am` обоих патчей на чистой распаковке, повторная сборка `_ldap` на Python 3.12 и повторные 72 теста, OK с одним исходным expected failure.
- Git tree восстановленного и рабочего дерева совпадает: `7dfa21e703844e13c250a964cc6a7209cf243f1c`.
