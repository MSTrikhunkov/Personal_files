# Обоснование применимости и исправлений

Дата: 2026-09-18. Объект: предоставленный тарбол `v0.5.1.tar.gz`, pyasn1 0.5.1. Анализ выполнен по исходникам тарбола и официальным security advisories/коммитам проекта pyasn1. Обновление библиотеки до 0.6.x не выполнялось.

## CVE-2026-30922 — применима, исправлена

В `SingleItemDecoder.__call__` файла `pyasn1/codec/ber/decoder.py` отсутствовал контроль глубины. Вложенные SEQUENCE/SET приводили к рекурсивным вызовам. Путь используется также CER/DER; защита требуется и для definite-length структур.

Перенесён счётчик глубины `_nestingLevel` и лимит 100 из [коммита 25ad481c19fdb006e20485ef3fc2e5b3eff30ef0](https://github.com/pyasn1/pyasn1/commit/25ad481c19fdb006e20485ef3fc2e5b3eff30ef0). Превышение отклоняется через `PyAsn1Error`. Защита относится к декодированию; новые ограничения кодирования не добавлялись.

До исправления 4 из 5 новых проверок не проходили: вложенность 200 принималась без предусмотренной ошибки. В отдельном воспроизведении 50 000 заголовков `30 80` приводили к `RecursionError`. После исправления тот же вход возвращает `PyAsn1Error` с сообщением о глубине. Проверены definite/indefinite, смешанные SEQUENCE/SET, схема, streaming, граница 100/101, соседние элементы и независимые последовательные вызовы.

[Официальное уведомление GHSA-jr27-m4p2-rc6r](https://github.com/pyasn1/pyasn1/security/advisories/GHSA-jr27-m4p2-rc6r): исправлено в апстриме 0.6.3.

## CVE-2026-59886 — применима, исправлена

`Real.__float__` в `pyasn1/type/univ.py` вычислял целочисленную степень до преобразования в float. Большой положительный показатель в коротком REAL-входе вызывает чрезмерные затраты при выводе, сравнении или преобразовании декодированного значения.

Без изменений перенесены production-hunks [коммита e60c691cb91addb8fcefa2f537e85ede6fb1e886](https://github.com/pyasn1/pyasn1/commit/e60c691cb91addb8fcefa2f537e85ede6fb1e886): `math.ldexp` для основания 2, ограничение положительного десятичного показателя, обработка нулевой мантиссы, целочисленное деление при десятичной нормализации.

Контрольный BER-вход `09 07 83 04 3b 9a ca 00 01` кодирует показатель 1 000 000 000. В отдельном процессе с CPU-лимитом 1 секунда исходная версия завершалась сигналом SIGXCPU (код -24), исправленная — штатно обрабатывала `OverflowError` (код 0). Нормализация `10**400` до исправления также воспроизводимо завершалась ошибкой, после — сохраняет точный tuple. Проверены переполнение, underflow, ноль, точность обычных значений, BER/CER/DER decode/encode больших показателей и `<overflow>`.

[Официальное уведомление GHSA-hm4w-wwcw-mr6r](https://github.com/pyasn1/pyasn1/security/advisories/GHSA-hm4w-wwcw-mr6r): исправлено в апстриме 0.6.4.

## CVE-2026-59884 — применима, исправлена

Цикл чтения long-form tag ID в BER-декодере не ограничивал число октетов. CER/DER наследуют этот путь. Дополнительно форматирование очень большого tag ID могло вызвать `ValueError` из-за лимита десятичного преобразования Python.

Перенесён [коммит 628e36ecbb5277a3f01572ce418ef54271b165a5](https://github.com/pyasn1/pyasn1/commit/628e36ecbb5277a3f01572ce418ef54271b165a5): лимит 20 октетов до увеличения целого, а также безопасное форматирование Tag/TagSet с hexadecimal fallback. Контекст объявления константы адаптирован к 0.5.1; защиту OID из другого CVE этот перенос не добавляет.

До исправления из пяти новых тестов было 2 failures и 1 error на Python 3.12. После все проходят. Проверены максимальный 140-битный tag ID, превышение на один октет, длинные незавершённые теги с ненулевыми и нулевыми continuation-группами, ранняя остановка streaming после не более 22 байтов, repr больших положительных/отрицательных tag ID и неизменность обычного repr.

[Официальное уведомление GHSA-m4p7-r5rc-7g4j](https://github.com/pyasn1/pyasn1/security/advisories/GHSA-m4p7-r5rc-7g4j): исправлено в апстриме 0.6.4.

## CVE-2026-59885 — применима к OBJECT IDENTIFIER, исправлена

В `ObjectIdentifierPayloadDecoder` и `ObjectIdentifierEncoder` на каждой дуге создавались новые tuple с копированием накопленных данных. Это даёт квадратичную стоимость по числу дуг, независимо от величины отдельной дуги.

Из [коммита 45bdb19eb7df4b3780fe9c912c63e99bffc39dd9](https://github.com/pyasn1/pyasn1/commit/45bdb19eb7df4b3780fe9c912c63e99bffc39dd9) перенесены все изменения OBJECT IDENTIFIER: list/append/extend, обратный порядок сборки октетов многобайтовой дуги и преобразование в tuple на прежних границах. Реализация общая для BER/CER/DER.

Часть RELATIVE-OID неприменима: в исходниках 0.5.1 отсутствуют `univ.RelativeOID`, `RelativeOIDPayloadDecoder` и `RelativeOIDEncoder`. Эти новые API намеренно не добавлялись. Неприменимость этой части не означает неприменимость CVE в целом.

Замер при 10 000 и 40 000 дополнительных однобайтовых дуг (минимум трёх прогонов, CPython 3.9.6):

| Операция | До, 10k / 40k, сек | Рост до | После, 10k / 40k, сек | Рост после |
|---|---:|---:|---:|---:|
| decode | 0.196343 / 3.149718 | 16.04 | 0.001420 / 0.005732 | 4.04 |
| encode | 0.195795 / 3.156266 | 16.12 | 0.000856 / 0.003114 | 3.64 |

Числа зависят от машины. Отдельный `tests/benchmark_security_oid.py` воспроизводит проверку масштабирования и не включён в обычный unittest discovery, чтобы не добавлять зависимость штатного набора от загрузки хоста. Функциональные тесты проверяют точные байты, ведущие пары дуг, многобайтовые дуги, native tuple, схемы и отклонение повреждённых OID.

[Официальное уведомление GHSA-8ppf-4f7h-5ppj](https://github.com/pyasn1/pyasn1/security/advisories/GHSA-8ppf-4f7h-5ppj): исправлено в апстриме 0.6.4.
