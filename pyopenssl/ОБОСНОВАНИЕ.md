# Обоснование исправлений pyOpenSSL 24.1.0

Проверка от 2026-09-18 относится к предоставленному `24.1.0.tar.gz`. Проанализированы оба уязвимых пути в исходниках и соответствующие официальные исправления pyca/pyopenssl. Оснований для признания этих CVE неприменимыми к библиотеке 24.1.0 нет; фактическая экспозиция приложения зависит от использования соответствующих callbacks.

## CVE-2026-27459 — применима, исправлена

В `_CookieGenerateCallbackHelper` (`src/OpenSSL/SSL.py`) результат пользовательского генератора cookie копировался в `unsigned char *` без проверки размера. Область доступна через публичный `Context.set_cookie_generate_callback` и DTLS. Указатель CFFI не сообщает размер настоящего OpenSSL-буфера, поэтому обычное slice-присваивание не предотвращает переполнение.

Перенесён [официальный коммит 57f09bb4bb051d3bc2a1abd36e9525313d5cd408](https://github.com/pyca/pyopenssl/commit/57f09bb4bb051d3bc2a1abd36e9525313d5cd408): перед записью проверяется длина, при превышении возникает `ValueError`, callback возвращает 0, а сохранённая ошибка передаётся существующим механизмом `raise_if_problem`. Применён именно upstream-лимит `getattr(_lib, "DTLS1_COOKIE_LENGTH", 255)`, а не число, выведенное из краткого текста CVE.

До исправления два новых теста с oversized-cookie не проходили: callback возвращал успех. Чтобы не повреждать память при воспроизведении, тесты выделяют заведомо больший C-буфер. После исправления подтверждается отказ до изменения буфера и выходной длины. Проверены размеры 0, 1, 255 и превышения лимита на 1 и 769 байтов. Дополнительно перенесён upstream-тест настоящего `DTLSv1_listen`, где ошибка cookie достигает Python; штатные DTLS и SRTP tests сохранены.

[Уведомление GHSA-5pwr-322w-8jr4](https://github.com/pyca/pyopenssl/security/advisories/GHSA-5pwr-322w-8jr4) указывает затронутые версии начиная с 22.0.0 и исправление в 26.0.0. Наш перенос не повышает версию пакета.

## CVE-2026-27448 — применима, исправлена

Обёртка в `Context.set_tlsext_servername_callback` не перехватывала исключение пользовательского callback. Исключение пересекало CFFI callback boundary, после чего handshake мог продолжиться. Поэтому приложение, использующее callback для проверки имени или другой политики доступа, могло получить соединение без успешного выполнения проверки.

Перенесён [официальный коммит d41a814759a9fb49584ca8ab3f7295de49a85aa0](https://github.com/pyca/pyopenssl/commit/d41a814759a9fb49584ca8ab3f7295de49a85aa0): добавлен импорт `sys`, `Exception` обрабатывается через `sys.excepthook(*sys.exc_info())`, и возвращается `SSL_TLSEXT_ERR_ALERT_FATAL`.

Upstream handshake-test адаптирован к стилю 24.1.0 без новых требований к аннотациям типов и дополнен вариантом без SNI. До исправления оба варианта завершались `DID NOT RAISE`: handshake не отклонялся. После возникает `OpenSSL.SSL.Error`, а `sys.excepthook` получает тот же экземпляр исключения с traceback ровно один раз. Существующие проверки успешных callbacks и их замены продолжают проходить.

[Уведомление GHSA-vp96-hxj8-p424](https://github.com/pyca/pyopenssl/security/advisories/GHSA-vp96-hxj8-p424) относит проблему к старым версиям начиная с 0.14 и указывает исправление в 26.0.0.

## Состав переноса и совместимость

Production-изменения ограничены `src/OpenSSL/SSL.py`: 14 добавленных строк и одна заменённая строка callback-вызова. Не перенесены посторонние изменения релиза 26.0.0, changelog этого релиза, повышение минимальной Python/cryptography и новые API. Изменения тестов находятся в существующем `tests/test_ssl.py`.

Публичные сигнатуры и metadata остаются прежними: pyOpenSSL 24.1.0, Python >=3.7, cryptography>=41.0.5,<43. Синтаксис изменений совместим с Python 3.7. Проверено выполнение на минимальной cryptography 41.0.5 и на 42.0.8. Python 3.7 не был доступен и не запускался. Прекращение принятия oversized-cookie и соединений с ошибкой SNI callback — намеренные изменения безопасности, совпадающие с апстримом.

Исходных случаев 504, добавлено 8, итоговых 512. В исходниках с минимальной зависимостью не прошёл `TestConnection.test_wantWriteError`; с 42.0.8 также не прошёл `TestMemoryBIO.test_unexpected_EOF`. Эти проверки зависят от поведения сетевого стека: первая ожидала `WantWriteError`, но получала `WantReadError`; вторая ожидала `(-1, 'Unexpected EOF')`, но получила macOS `ECONNRESET` (54). В итоговом полном запуске с 42.0.8 остался первый сбой, остальные прошли. Изменчивость результатов подтверждает нестабильность этих исходных проверок в данном окружении; тесты и production-код ради их обхода не менялись.

Для дополнительной проверки выполнен отдельный запуск на 42.0.8:

```sh
PYTHONPATH=src ../.venv-max/bin/python -m pytest -q \
  --deselect=tests/test_ssl.py::TestConnection::test_wantWriteError \
  --deselect=tests/test_ssl.py::TestMemoryBIO::test_unexpected_EOF
```

Результат: 509 passed, 1 skipped, 2 deselected. Единственный штатный skip — Linux-specific проверка fallback trust paths, неприменимая к macOS. Три предупреждения полного набора относятся к уже deprecated `sign`, `verify` и строковому cipher list; они присутствовали до изменений.
